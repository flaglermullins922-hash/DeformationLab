> 目标：不只看懂"这段代码在干什么"，而是理解**为什么这么写**，最后能**自己独立从零做出来**。
> 配套文件：`Assets/Scripts/Runtime/` 与 `Assets/Scripts/Editor/` 下的源码。

## 第 0 章 先建立全局观：回答三个问题

### 0.1 这个作业到底在考什么？

作业原文拆成四句：

1. 能导入 obj 文件；
2. 能通过按钮选择变形；
3. 必须实现**锥化 / 扭曲 / 弯曲**三种变形；
4. 必须实现 **FFD**：初始状态 = 算包围盒得到 n×n×n 网格点；终止状态 = 修改网格点、观察模型变化。

背后的知识点其实是**计算机图形学里"全局变形（Global Deformation）"这一章**：怎么用数学规则，对模型上成千上万个顶点"批量"变换，让整个模型变形。

### 0.2 四种变形有什么共同点？

这是整份代码的灵魂，想通这一点，四种变形就从一个"知识点"变成一个"套路"：

> **先算一个归一化参数 t ∈ [0,1]（顶点在主轴上的相对位置），再让"变换量"随 t 变化。**

- 锥化：缩放量 `s(t) = 1 + k·t`，随高度线性变
- 扭曲：旋转角 `θ(t) = angle·t`，随高度线性累加
- 弯曲：把直线主轴映射到圆弧，弧角随高度线性累加
- FFD：换了个思路（下面单独讲），但本质也是"用位置决定变换量"

所以代码里第一件事，一定是**找主轴、算包围盒、算 t**。

### 0.3 代码为什么要分四层？

```
渲染层   DeformationUI / DeformationInteraction / Factory / Controller（大脑）
模型层   DeformableModel（顶点访问）/ ProceduralMeshBuilder（内置模型）
数学层   DeformMath（三种解析变形）/ FfdLattice（FFD）
解析层   ObjParsing / ObjMeshBuilder（运行时 OBJ 解析）
```

分层的唯一目的：**把"数学"和"Unity"彻底分开**。

- 数学层（DeformMath、FfdLattice）是**纯函数/纯数据类**：不碰 GameObject、不碰场景、不碰渲染。输入一个顶点，输出一个新顶点。
- 这样做的最大好处是**可以单元测试**：直接写个脚本断言"顶点 (1,1,0) 绕 Y 轴转 90° 应该变成 (0,1,-1)"，不用打开 Unity 看画面就知道公式对不对。

这一层设计，是整个工程能"一次做对、还能自动验证"的根基。

## 第 1 章 数学原理（手把手推导 + 逐行对应代码）

### 1.1 共同地基：归一化参数 t

**为什么要归一化？** 假如模型高 10 米，另一个高 1 米，我们想"让顶端缩一半"。如果直接写 `缩放 = 高度坐标 × 系数`，两个模型用同一个系数会得到完全不同的效果。归一化后，无论模型多高，`t` 都落在 [0,1]，变形效果只和"在模型的哪个相对位置"有关，和绝对尺寸无关。

公式（`DeformMath.AxisParam`）：

```
t = (p[axis] - min[axis]) / (max[axis] - min[axis])      t ∈ [0,1]
```

对应代码：

```csharp
public static float AxisParam(Vector3 p, Vector3 min, Vector3 max, DeformAxis axis)
{
    float span = max[(int)axis] - min[(int)axis];   // 主轴高度 H
    if (Mathf.Abs(span) < 1e-6f) return 0f;          // 高度≈0，防除零
    return (p[(int)axis] - min[(int)axis]) / span;
}
```

- `axis` 是枚举（X/Y/Z），`(int)axis` 把枚举当数组下标用，直接取 `p.x/p.y/p.z` 里对应的那一个。
- `t = 0` 是模型最底端，`t = 1` 是最顶端（以 Y 轴为例）。

### 1.2 Taper 锥化

**直觉**：把一根竖直橡皮泥柱，每层高度按"越往上缩得越多"的比例去挤/拉，就得到锥形。

**公式推导**：

在垂直于主轴的平面内做缩放，缩放系数随 t 线性变化：

```
s(t) = 1 + k·t
```

- `k > 0`：顶部放大（上粗下细）
- `k < 0`：顶部收窄（上尖下宽）
- `k = 0`：不变

对垂直主轴的每个坐标 c（主轴那个坐标不动）：

```
p'[c] = center[c] + (p[c] - center[c]) · s(t)
```

其中 `center` 是包围盒中心。**为什么要绕中心缩放，而不是绕原点？** 因为如果绕原点，模型整体会往一边跑（漂移）；绕中心线缩放，模型才"原地变粗变细"。

对应代码（`DeformMath.Taper`）：

```csharp
public static Vector3 Taper(Vector3 p, Vector3 min, Vector3 max, DeformAxis axis, float k)
{
    float t = AxisParam(p, min, max, axis);   // ① 归一化位置
    float s = 1f + k * t;                     // ② 缩放系数
    Vector3 center = (min + max) * 0.5f;      // ③ 中心线
    Vector3 r = p;
    for (int c = 0; c < 3; c++)               // ④ 遍历 x/y/z
        if (c != (int)axis)                   //    主轴不缩放
            r[c] = center[c] + (p[c] - center[c]) * s;
    return r;
}
```

一个值得注意的细节：`for (int c = 0; c < 3; c++) if (c != axis)` 这种写法，让这段代码对 X/Y/Z 三种主轴**通用**，不用为每种轴写一份。

### 1.3 Twist 扭曲

**直觉**：抓住模型上下两端反方向一拧，就成麻花。每层转的角度不一样，越往上拧得越狠。

**公式推导**：

绕主轴旋转，角度随 t 线性累计：

```
θ(t) = angle · t
p' = center + R(axis, θ(t)) · (p - center)
```

- `t=0`（底部）：`θ=0`，不转
- `t=1`（顶部）：`θ=angle`，转满整个角度

绕 Y 轴的旋转矩阵（右手系，与 Unity `Quaternion.AngleAxis` 一致）：

```
x' = x·cosθ + z·sinθ
y' = y
z' = -x·sinθ + z·cosθ
```

对应代码（`DeformMath.Twist` + `RotateAroundAxis`）：

```csharp
public static Vector3 Twist(Vector3 p, Vector3 min, Vector3 max, DeformAxis axis, float angleRad)
{
    float t = AxisParam(p, min, max, axis);
    float theta = angleRad * t;                      // 角度随高度线性累计
    Vector3 center = (min + max) * 0.5f;
    return center + RotateAroundAxis(p - center, axis, theta);   // 绕中心线转
}

public static Vector3 RotateAroundAxis(Vector3 v, DeformAxis axis, float theta)
{
    float c = Mathf.Cos(theta), s = Mathf.Sin(theta);
    switch (axis)
    {
        case DeformAxis.X: return new Vector3(v.x, v.y * c - v.z * s, v.y * s + v.z * c);
        case DeformAxis.Y: return new Vector3(v.x * c + v.z * s, v.y, -v.x * s + v.z * c);
        default:           return new Vector3(v.x * c - v.y * s, v.x * s + v.y * c, v.z);
    }
}
```

**为什么是 `p - center` 再 `center + ...`？** 和锥化同理：绕中心线转，模型才"原地拧"，不会甩出去。

`RotateAroundAxis` 手写了三个轴的旋转矩阵，而不是直接用 `Quaternion.AngleAxis`——因为自检脚本里要和 Unity 的旋转**对拍验证**，手写矩阵能证明"我们自己的公式也对"。

### 1.4 Bend 弯曲（三种里最绕的，重点讲）

**直觉**：把一根直的软管贴到半径为 R 的圆筒外壁上，软管就弯成弧形。

**完整几何推导**（一步步来）：

设弯曲角 θ（弧度），主轴高度 H。弯曲半径就是：

```
R = H / θ       （弧长 H 对应圆心角 θ，所以半径 = 弧长/圆心角）
```

取弯曲中心在主轴的坐标 `yc`（`center01` 指定它在主轴上的相对位置，0.5 = 中间）。

对每个顶点，先算它**相对弯曲中心的弧长**：

```
s = p[axis] - yc
```

该顶点在圆弧上对应的**圆心角**：

```
φ = s / R       （弧长 = 半径 × 圆心角）
```

再算顶点在弯曲方向上、相对中心线的**偏移**：

```
off = p[bendDir] - cDir        （cDir 是弯曲方向上的中心）
```

弯曲后的两个坐标：

```
new(bendDir) = R·(1 - cosφ) + off·cosφ
new(axis)    = yc + R·sinφ  - off·sinφ
```

**为什么是这个公式？验证三个直觉：**

1. **中心线上的顶点（off = 0）**：`new(bendDir) = R(1-cosφ)`，`new(axis) = yc + R·sinφ`。这正好是**标准圆弧参数方程**（圆心在弯曲内侧、半径 R）。✓
2. **θ → 0（几乎不弯）**：`R → ∞`，`sinφ ≈ φ`，`cosφ ≈ 1`，代入后 `new(bendDir) ≈ off`，`new(axis) ≈ p[axis]`，即**不变**。✓
3. **弯曲方向**：θ > 0 往 +bendDir 弯，θ < 0 往反方向弯（因为 R = H/θ 带符号）。✓

对应代码（`DeformMath.Bend`）：

```csharp
public static Vector3 Bend(Vector3 p, Vector3 min, Vector3 max, DeformAxis axis,
                           float bendDeg, float center01, DeformAxis bendDir)
{
    float H = max[(int)axis] - min[(int)axis];
    if (Mathf.Abs(H) < 1e-6f) return p;         // 高度≈0，无法弯
    float theta = bendDeg * Mathf.Deg2Rad;
    if (Mathf.Abs(theta) < 1e-4f) return p;     // 几乎不弯 → 恒等（防 R→∞ 溢出）

    float lo = min[(int)axis];
    float yc = lo + center01 * H;               // 弯曲中心的轴坐标
    float s = p[(int)axis] - yc;                // 相对弯曲中心的弧长
    float cDir = (min[(int)bendDir] + max[(int)bendDir]) * 0.5f;
    float off = p[(int)bendDir] - cDir;         // 弯曲方向的偏移

    float R = H / theta;                        // 弯曲半径（带符号）
    float phi = s / R;
    float cosPhi = Mathf.Cos(phi), sinPhi = Mathf.Sin(phi);

    float newOff = R * (1f - cosPhi) + off * cosPhi;   // 沿 bendDir 的新偏移
    float newLen = yc + R * sinPhi - off * sinPhi;     // 沿 axis 的新位置

    Vector3 r = p;
    r[(int)axis] = newLen;
    r[(int)bendDir] = cDir + newOff;
    return r;
}
```

两个细节：`bendDeg * Mathf.Deg2Rad` 是"角度转弧度"；`if (theta < 1e-4) return p` 是对 θ→0 时 `R = H/θ` 会变成无穷大的**短路保护**（数学上退化为恒等变换）。

### 1.5 FFD 自由变形（Free-Form Deformation）

前三种是"解析式"——变形规则是写死的公式。FFD 是"格子驱动"的通用变形，**Sederberg & Parry 1986** 年提出，是自由变形的开山之作。

#### 核心思想：把模型"装进"一个格子

1. 算模型包围盒；
2. 在包围盒上均匀摆 `n×n×n` 个**控制点**（默认 n=4，每边 4 个，共 64 个）；
3. 把每个顶点"嵌入"格子里，记下它在格子里的**参数坐标 (s,t,u)**；
4. 之后**只动控制点**，顶点通过 Bernstein 权重自动跟随。

**最关键的一点**：顶点的参数坐标 (s,t,u) 在嵌入后**永不改变**。拖动的是控制点，顶点"粘"在参数空间里被动跟随——这正是 FFD 与"直接拖顶点"的本质区别。

#### 四步法（对应作业要求的两阶段）

**① 初始状态**（`FfdLattice.Build`）：算包围盒，均匀摆控制点：

```
P[i,j,k] = min + (i/(n-1))·dx + (j/(n-1))·dy + (k/(n-1))·dz
```

这就是作业要求的"初始状态：通过计算模型包围框，得到 n×n×n 的网格点坐标"。

**② 嵌入**（`FfdLattice.Embed`）：顶点 → 参数坐标。初始格子均匀，所以就是简单线性归一化：

```
s = (v.x - min.x) / dx
t = (v.y - min.y) / dy
u = (v.z - min.z) / dz
```

**③④ 变形**（`FfdLattice.Deform`）：移动控制点后，顶点新位置 = Bernstein 张量积：

```
v' = Σᵢ Σⱼ Σₖ Bᵢ(s)·Bⱼ(t)·Bₖ(u) · P[i,j,k]
```

这就是作业要求的"终止状态：通过修改网格点坐标，观察模型变化"。

#### Bernstein 基函数

```
Bᵢ(u) = C(m,i) · uⁱ · (1-u)^(m-i)      m = n-1（次数）
```

- n=2：线性（等价三线性插值）
- n=3：二次
- n=4：三次（最经典，默认）

#### 为什么 Bernstein 张量积能"黏住"顶点？

关键性质：**Bernstein 基构成单位分解**，即对任意 u，`Σᵢ Bᵢ(u) = 1`。于是：

- 控制点不动时，`v' = v`（恒等变换，自检里专门验证）；
- 只动一个角点时，顶点移动量 = `B₃(s)·B₃(t)·B₃(u)` × 角点位移——**离角点越近动得越多，越远动得越少**，平滑过渡。

对应代码（`FfdLattice.cs` 全文）：

```csharp
public void Build(Bounds bounds, int resolution)      // ① 初始状态
{
    n = Mathf.Clamp(resolution, 2, 4);
    origin = bounds.min;
    size = bounds.size;
    initial = new Vector3[n, n, n];
    current = new Vector3[n, n, n];
    float div = Mathf.Max(1, n - 1);
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            for (int k = 0; k < n; k++)
            {
                Vector3 p = new Vector3(
                    origin.x + size.x * i / div,
                    origin.y + size.y * j / div,
                    origin.z + size.z * k / div);
                initial[i, j, k] = p;          // 存两份：初始（可复位）+ 当前（可拖）
                current[i, j, k] = p;
            }
}

public Vector3 Embed(Vector3 v)                 // ② 嵌入
{
    return new Vector3(
        (v.x - origin.x) / (size.x + 1e-6f),
        (v.y - origin.y) / (size.y + 1e-6f),
        (v.z - origin.z) / (size.z + 1e-6f));
}

public Vector3 Deform(Vector3 param)            // ③④ 变形
{
    float s = Mathf.Clamp01(param.x);
    float t = Mathf.Clamp01(param.y);
    float u = Mathf.Clamp01(param.z);

    // 预计算三个方向的 Bernstein 基（3n 次，而非 n³ 次，提速）
    float[] bs = new float[n], bt = new float[n], bu = new float[n];
    for (int i = 0; i < n; i++) { bs[i] = Bernstein(i, s); bt[i] = Bernstein(i, t); bu[i] = Bernstein(i, u); }

    Vector3 result = Vector3.zero;
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            for (int k = 0; k < n; k++)
                result += current[i, j, k] * (bs[i] * bt[j] * bu[k]);   // 张量积
    return result;
}

public float Bernstein(int i, float u)
{
    int m = n - 1;
    return Binomial(m, i) * Mathf.Pow(u, i) * Mathf.Pow(1f - u, m - i);
}
```

一个性能细节：`Deform` 里先算好 `bs/bt/bu` 三个数组（各 n 次），再在三重循环里**复用**。如果直接在三重循环里每次都算 `Bernstein`，复杂度会从 `3n + n³` 变成 `3·n³` 次幂运算——对 n=4 是 64 个点、每个顶点都要算，累积起来会明显变慢。这是"先算基函数、再张量积"的经典优化。

## 第 2 章 怎么做出来的：工程实现路径

### 2.1 四个关键设计决策（想清楚了再动手）

#### 决策一：变形函数写成"纯函数"

`DeformMath` 全是 `static` 函数，输入"原始顶点 + 包围盒 + 参数"，输出"新顶点"，**不碰任何 Unity 组件、不读写任何全局状态**。

好处：
- 可复现（同样输入永远同样输出）；
- 可单元测试（写断言直接验证）；
- 可复用（换引擎都能用）。

#### 决策二：从 `RestVertices`（初始顶点）出发计算，而不是从"当前顶点"累加

看 `DeformationController.ApplyDeformation`：

```csharp
Vector3[] src = model.RestVertices;   // 永远从初始顶点出发
```

为什么要这样？**防止误差累积**。如果每次变形都基于"上一次变形后的顶点"，反复调参数（比如把锥化系数从 -0.6 拖到 0.8 再拖回来）会让浮点误差一点点累积，最后模型"回不去了"。从初始顶点出发，每次都是干净的一次计算。

`RestVertices` 在 `DeformableModel.FinishLoad` 里存好，是所有变形的"基准姿势"。

#### 决策三：运行时自己解析 OBJ（而不是用 Unity 的 AssetDatabase 导入）

作业要求"能导入 obj 文件"。Unity 的模型导入是在编辑器里做的（生成不可读写的 `.asset`），而我们要**运行时读顶点、改顶点**，所以必须自己写解析器：把 `.obj` 文本逐行解析成顶点/法线/UV/三角形，再自己建一个**可读写的 Mesh**。

这正是"解析层"存在的理由——`ObjParsing` + `ObjMeshBuilder` 复用自上一个作业 ObjViewer。

#### 决策四：场景零拖拽（纯代码搭建）

`DeformationController.Awake` 里用代码创建相机、灯光、地面、模型、UI、交互，**不用在 Inspector 里手动拖任何引用**。好处：整个工程是"代码即文档"，别人（或未来的你）拉下来就能跑，不会因为少拖一个引用而报错。

### 2.2 顶点数据管线（一条完整的数据流）

以"点锥化按钮"为例，走一遍完整流程：

1. 用户点「锥化」→ `DeformationUI.OnModeButton` → `controller.SetMode(Taper)`；
2. `SetMode` → `ApplyDeformation()`；
3. `ApplyDeformation` 取 `model.RestVertices`（初始顶点）+ `model.ModelBounds`（包围盒），遍历每个顶点调 `DeformMath.Taper(...)`；
4. 得到的新顶点数组 `dst`，通过 `model.SetVertices(dst)` 写回每个子网格的 `Mesh`；
5. `model.RecalculateNormalsAndBounds()` 重算法线（**顶点动了，法线必须跟着更新，否则光照方向错、模型看起来黑一块亮一块**）。

`DeformableModel.SetVertices` 里做了一件事：因为模型可能有多个子网格（一个 OBJ 里多个 `o`/`usemtl`），所以把"合并的大数组"按 `PartOffsets` 切回每个子网格、分别 `mesh.SetVertices(slice)` 写回。

### 2.3 FFD 控制点交互：拾取与拖拽

`DeformationInteraction` 里最值得学的是**拾取方案**：

- **为什么不用 `Physics.Raycast`？** 那需要给每个控制点小球加 Collider，64 个控制点就要 64 个碰撞体，还要设层、处理遮挡，麻烦且不精确。
- **改用屏幕空间投影 + 像素阈值**（`PickHandle`）：把每个控制点 `WorldToScreenPoint` 投影到屏幕，算它离鼠标像素点的距离，取最近且在阈值内的那个。纯数学、零碰撞体、还天然支持"离得近优先"。

拖拽则把鼠标移动约束在"过控制点、垂直于相机视线"的平面上（`new Plane(-cam.forward, hp)`），这样鼠标往哪拖、控制点就往哪走，符合直觉不别扭。

## 第 3 章 怎么验证"做对了"

### 3.1 纯函数 → 可自动化自检

因为数学层是纯函数，所以可以直接写**17 项数学断言**（`DeformSelfTest.cs`），逐条验证公式对不对：

| 变形 | 验证什么数学性质 |
|---|---|
| Taper | k=0 恒等；主轴坐标不变；垂直轴按 s 缩放；中心线不动 |
| Twist | angle=0 恒等；顶部转满角、底部不转；**与 Unity Quaternion 对拍一致** |
| Bend | θ=0 恒等；中心线顶点落圆弧；弧角正确；z 坐标不变 |
| FFD | 初始格子重建=恒等；Bernstein 单位分解 ΣB=1；线性精度；移动角点→顶点按权重跟随；Reset 恢复 |

其中"与 Unity Quaternion 对拍""Bernstein 单位分解 ΣB=1"是**教科书级的性质验证**——用数学定义本身去检验实现。

批处理跑（不需要打开 GUI）：

```bash
Unity.exe -batchmode -projectPath <工程> -executeMethod DeformationLab.EditorTools.DeformSelfTest.RunFromCLI -quit
```

### 3.2 视觉验收：命令行自动截图

数学对了还不够，还得"眼睛看见"变形效果对不对。`DevAutoShot.cs` 支持命令行启动 → 设模式 → 渲染一帧 → 截图 → 退出：

```
DeformationLab.exe -shot out.png -mode bend -amount 90 ...
```

这样能自动化地截出"锥化/弯曲/FFD"各一张图，人工核对一眼。

## 第 4 章 踩过的坑（真实经验，下次别再犯）

1. **缺 `com.unity.ugui` 包**：运行时用代码搭 UGUI，但这个包默认可能没装 → 直接复制上一个工程（BezierCurveLab）的 `Packages/manifest.json`。
2. **构建版 `Shader.Find("Standard")` 返回 null**：内置 Standard shader 如果没被任何材质引用，会被构建**剥离**，运行时创建材质就抛空引用。→ 自己写 Unlit shader，并加进 `GraphicsSettings` 的 Always Included Shaders。
3. **`GetAllCurrentVertices` 循环依赖**：`VertexCount` 属性读 `RestVertices.Length`，而 `RestVertices` 又在 `FinishLoad` 里才赋值 → 时序错。→ 理清初始化顺序，先赋值再访问。
4. **UI 构建 `CreateRect` 没传背景色却 `GetComponent<Image>()`**：返回的 Image 是 null，后续控件全空。→ 统一"传了背景色才 AddComponent<Image>"。
5. **Controller.Awake 里同步加载触发 UI 回调，但 UI 的 Start 还没跑**（时序）：加载完成回调里访问 UI 组件时为 null。→ UI 在加载前装配好，回调里做空判断。

这些坑的共同点：**都是"运行时用代码搭场景/搭 UI"特有的时序和资源问题**——因为绕过了 Unity 编辑器的自动装配，很多编辑器里帮你处理好的事（shader 不被剥离、引用自动填充）都得自己兜底。

## 第 5 章 如果让你从零重做（step-by-step 清单）

1. **拆需求**：导入 OBJ / 按钮选变形 / 三种解析变形 / FFD 两阶段。
2. **写数学层（纯函数，先不碰 Unity 渲染）**：
   - `AxisParam` 归一化 t；
   - `Taper`（s = 1+k·t）；
   - `Twist`（θ = angle·t，绕轴旋转矩阵）；
   - `Bend`（R=H/θ，圆弧映射）；
   - `FfdLattice`（Build → Embed → Deform，Bernstein 张量积）。
3. **写自检**：用纯数学断言验证上面每个公式（尤其"单位分解""与 Unity 对拍"）。
4. **写解析层**：复用 OBJ 解析器，建可读写 Mesh。
5. **写模型层**：`RestVertices`（基准）+ `SetVertices`（写回）+ `RecalculateNormals`。
6. **写控制层**：`ApplyDeformation` 从 RestVertices 出发算 → 写回；FFD 的 Build/拖动/Reset。
7. **写交互层**：轨道相机 + FFD 屏幕空间拾取。
8. **写 UI 层**：按钮/滑块/参数面板。
9. **构建 exe + 截图验收**。
10. **推 GitHub + 写 README/代码导读**。

按这个顺序，每一步都能独立验证，不会"攒到最后一起崩"。

## 附录：核心词汇表

| 术语 | 含义 |
|---|---|
| 包围盒 Bounding Box | 包住模型的最小立方体 `[min, max]` |
| 主轴 Axis | 变形的长度方向（默认 Y） |
| 归一化参数 t | 顶点在主轴上的相对位置 [0,1] |
| 纯函数 | 输出只由输入决定、无副作用的函数 |
| RestVertices | 初始顶点数组（变形基准） |
| Bernstein 基 | `C(m,i)·uⁱ·(1-u)^(m-i)`，FFD 的权重函数 |
| 单位分解 | 基函数之和恒等于 1（ΣB=1） |
| 张量积 | 多维基函数的乘积（三线性/三次插值的推广） |
| 顶点色 Vertex Color | 存在顶点上的颜色，变形后跟着顶点走 |
| 法线 Normal | 顶点朝向，决定光照，顶点动后需重算 |
